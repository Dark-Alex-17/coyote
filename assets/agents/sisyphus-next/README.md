# sisyphus-next (CANDIDATE, upstream variant)

The decomposed sisyphus orchestrator as a session graph. Status: candidate - no agent
lists it as spawnable; the shipped `sisyphus` keeps running the prose protocol until
the artifact-equivalence replay passes and this directory replaces it.

## Shape

- **Spine** - script nodes (`scripts/gates.py`, one thin entry per node) own routing,
  every named loop bound, the ledgers, sentinel parsing and prompt assembly.
- **Judgment** - short single-question llm nodes with schemas; every schema carries the
  optional `anomalies` field.
- **Islands** - `coder`, `review-gauntlet`, `explore`/`librarian` (map fan-outs; team
  mode = `teammates: true`), `oracle`, `architecture-reviewer`, `step-runner`,
  `whetstone`, `engineer` (tier-3 consult) run as agent nodes exactly as shipped.
- **Durable run state** - `<cache dir>/sisyphus-next/runs/<run_id>/`, where the cache dir
  is `COYOTE_CACHE_DIR`, else `$XDG_CACHE_HOME/coyote`, else the platform cache directory
  (`~/Library/Caches/coyote` on macOS, `~/.cache/coyote` on Linux, `%LOCALAPPDATA%\coyote`
  on Windows); `SISYPHUS_RUNS_ROOT` overrides the whole path. The run dir holds the brief,
  state.json, context pack, decisions ledger, anomalies and report. A prompt containing
  `Sisyphus run id: <id>` re-enters that run; a run parked on a discussion also keeps its
  full state in `parked-state.json` until one `continue` resumes it.

Variables mirror `sisyphus` (names and defaults identical), except the graph-only
`pr_tracking` (see the graph-only variables row below). The session block routes
work to the graph and conversation to the `engineer` chat lane (`chat_agent_for: sisyphus`).

`\b(cargo|rustc|npm|pnpm|yarn|pytest|mvn|gradle|just)\b|\bgo (test|build|run)\b` against every
line of `graph.yaml` and of each `scripts/*.py` except `smoke_test.py`, and fails on any hit.

## Bare go-ahead intake and typed replies

Twelve nodes carry the two features: `confirm_handoff`, `draft_brief` (llm),
`draft_route`, `draft_fault`, `confirm_draft`, `draft_edit` (input), `interpret_reply` (llm),
`interpret_route`, `choice_park`, `choice_resume`, `choice_reask` and `end_discussion`. Every
one is reached only through a script `_next` edge; `intake` keeps `next: assess` as its
static default.

Handoff pickup: a top-level run (no `## SOURCE OF TRUTH`, `TASK-NNN` or teammate roster in
the message, and not `parallel=1`) whose message is a bare go-ahead looks for the engineer's
newest ready handoff. A bare go-ahead is an empty message or one of at most
`GO_AHEAD_WORDS_MAX` (12) words drawn only from `GO_WORDS` ("go", "do", "start",
"proceed", ...) and `GO_AHEAD_FILLER` ("okay", "ahead", "and", "get", "it", ...), with at
least one go word: "okay, go ahead and get started", "do it", "go for it" and "let's do it"
(curly apostrophes are normalized first) are, "go ahead and fix the flaky test" and "execute
the handoff at <path>" are not. The search reads
`plans/engineer-handoffs/*.md` under `project_dir` and the git root, keeps handoffs with
`status: ready`, `vehicle: sisyphus` and a `project:` that resolves to either, and takes the
newest by `created:` (ISO-8601, a trailing `Z` as UTC; the mtime when it does not parse). A
`vehicle: architect` handoff, or one with no `vehicle:` key (architect seeds predate the
key), is left alone. The confirmation is a hard-trigger `handoff_confirm` escalation, so it
reaches `confirm_handoff` through `escalate_gate` and `ask_dispatch` even under
`escalation_policy=autonomous`: "Use this handoff" makes the handoff's body (its frontmatter
dropped) the brief, re-reads its quality bar and goes to `assess`; a reply whose first token
is a typed path uses that file instead; "Give a handoff path instead" asks for one
(`handoff_path`, which accepts a typed path); "Draft a brief from this conversation instead"
drafts as below; "Abort the run" ends it. A typed path counts only when the reply is the path
alone, ends in `.md`, and resolves (relative to `project_dir`, then the git root, through
symlinks) to a file under the project's `plans/` or in an `engineer-handoffs` directory inside
the project; anything else goes to `interpret_reply`. The handoff is marked `status: consumed`
(with `consumed_by` and `consumed_at`, one atomic rewrite that keeps the file's line endings
and never writes an unreadable or empty file) in `route_intent`, only when work starts
(`next_subtask`, `plan_subtasks`, `architecture_review` or `run_step`) after an `assess` that
did not fault: a redirect, a clarifying question, a research answer, a block or an `assess`
fault (`assess_fault` sets `assess_faulted`) leaves it ready, with a ledger line. Only a
`status: ready`, `vehicle: sisyphus` handoff is consumed; a typed path to an architect seed or
a handoff with no `vehicle:` serves as the brief and stays ready, ledgered. An explicit
"execute the handoff at <path>" is not a bare go-ahead and is classified by `assess` as before.

Drafted brief: a top-level bare go-ahead with no ready handoff and non-blank
`{{previous_turns}}` (the engine seeds the session transcript, as for architect-next) goes
to `draft_brief`, which drafts a brief in the delegation shape from the message and the
earlier turns. `draft_route` writes it to `brief-draft.md` in the run dir and raises a
hard-trigger `draft_confirm` escalation (`confirm_draft`): "Use this draft" makes it the
brief and goes to `assess`, "Edit the draft" asks for changes through `draft_edit`, and any
other typed reply is taken verbatim as the requested changes; redrafts are bounded by
`DRAFT_ROUNDS_MAX` (3). `apply_answer` reads `draft_confirm` before any abort check, so "do
not abort on empty lists" redrafts. A draft fault, a `draft_possible: false` draft and the
redraft cap all fall back to today's behaviour: `assess` classifies the message as is. With
no earlier turns, `assess` does so straight away.

Typed replies: a reply to an escalation is matched to an option by number or text first. The
first reply that names no option goes to the `interpret_reply` llm node with the question,
the reply and the instructions the kind accepts (`ACCEPTED_INSTRUCTIONS`: `answer` for
`clarify` and `design_ask`, `design` for `design_choice`, `amendment` for `plan_defect`,
`recipe` for `probe_gap`, `rescope` for `scope_breach`, `path` for `handoff_confirm` and
`handoff_path`). `interpret_route` acts on the verdict: an option counts only when the
interpreter names it exactly or by its number; an accepted free-form instruction is applied
with the owner's own words verbatim inside the answer prefix `apply_answer` keys on (for
example `Continue; treat the criterion as amended: <reply>`); an unaccepted or unapplicable
instruction, or a loose option name, is unclear; unclear gets ONE clarifying question,
written into the escalation itself, after which an unmatched reply takes today's re-ask; an
interpreter fault falls back to that re-ask. `apply_answer` decides stop and abort from the
whole reply or an exact stop or abort option only (`_whole_reply_stop`), so "re-scope to add
src/x.rs; never abort the batch" proceeds; that holds for `oracle_fault`, `engine_fault`,
`plan_defect`, `review_incomplete`, `scope_breach`, the `strikeout` / `lane_stuck` /
`review_exhausted` family and `pr_review_owner_judgment` ("please address these, don't stop" is
a fix round), each keeping its default. On `clarify`, whose options assess writes, only a bare
stop word or the fixed "Abort" option `assess_fault` adds (the escalation's `stop_options`)
stops: "Stop using the in-memory cache" is an answer. Delegated runs interpret their
escalations the same way; `draft_confirm` and option-less escalations are not interpreted.

Discussion park: a reply the interpreter reads as a discussion parks the run. `choice_park`
sets the exposed `discussion` (kind, question, options with the recommended one marked, the
reply, the task), carries `discussion_run_id` into the next run, saves the run state (without
the graph variables, `initial_prompt` and `previous_turns`) to `parked-state.json` and ends
at `end_discussion` with a `SISYPHUS_AWAITING_DISCUSSION`
message naming the run id. The next message `continue` restores the parked run and asks the
question again; `continue: <answer>` takes the answer through `parse_answer` like a fresh
reply; `resume` is an alias; a parent orchestrator resumes with `Sisyphus run id: <id>` plus
the continue line. A delegated run ends that message with one more line for the parent,
`Discussion data: <json>`: a single-line JSON object with `kind`, `question`, `options` (each
a `text` and a `recommended` flag), the `reply` that parked it and the `run_id`, so the
parent can relay the question without parsing the prose. architect-next relays it this way:
it parks its own run on the question, and on the owner's `continue: <answer>` it resumes
this run with exactly `Sisyphus run id: <id>` and `continue: <answer>` on two lines (its
README's Delegated discussions paragraph). The live graph variables are never restored from
the park (`project_dir` is made absolute, and a git root that no longer matches the parked
one is ledgered while the parked one is kept), the re-ask count starts over, and the parked
state is removed on resume,
so a later continue starts fresh. Any other message, prose such as `continue please`
included, starts a fresh run and leaves the park. One question (its kind plus the text it was
first asked with) parks at most `DISCUSSION_PARKS_MAX` (3) times, so a new escalation of the
same kind gets its own budget; past the cap `choice_reask` asks again and the next reply is
matched without interpreting it. The parked run works the same for a delegated child: its
escalation reaches the root user through the parent.

## Multiple-choice prompts and the sizing verdict

Multiple-choice prompts: every escalation goes through `raise_escalation` in `gates.py` (the
`scope_breach` escalation, set directly, calls `normalize_choices` itself). An escalation
whose options, once texts that differ only in case collapse to one (the recommended copy
kept, ledgered), number `CHOICE_OPTIONS_MIN` to `CHOICE_OPTIONS_MAX` (2-4) with at least one
recommended (several keep the first, ledgered) is asked as a multiple choice: the
recommended option moves first, `data.multiple_choice` is set, and `_terminal_prompt` picks
`ask_choice_2`, `ask_choice_3` or `ask_choice_4` by the option count. The prompt body lists
each option's text and evidence under its static label, `Option 1 (recommended)` through
`Option 4`, and the engine adds its own `Other (custom)` choice. That covers every kind with
options, `clarify`'s LLM-written ones included. Kinds with more than 4 options, fewer than 2
or none recommended keep today's typed prompt (`ask_user`) with their options untouched;
`handoff_confirm`, `draft_confirm` and `review_incomplete` keep their own approval nodes
(`OWN_PROMPT_KINDS`). `parse_answer` counts a label, a number or an option's text as a pick
only when nothing but punctuation follows it (`_choice_pick`), so "Option 2, but only for
reads" names no option and, like any typed Other reply, goes through the existing
`interpret_reply` path: an option, an instruction the kind accepts, a discussion park, or one
clarifying question asked at the same multiple-choice prompt. There is no second classifier,
and the stop and abort hardening is unchanged (`_whole_reply_stop`, `clarify` with its
`stop_options`). Once `REASK_MAX` re-asks are spent, an empty reply to a multiple-choice
prompt takes the recommended option, with a ledger line; at the typed prompt the empty text
still stands. A hard trigger is the user's call, so an empty reply to a hard-trigger
multiple-choice prompt never takes its recommended option: the empty text stands, and on
`sizing_verdict` that picks no option, so the run ends at `end_redirect` and writes nothing.
A whole reply that is a stop word ("abort", "stop", ...) on a kind whose answer reads a stop
(`STOP_AWARE_KINDS`) goes straight to `apply_answer` instead of being interpreted or
re-asked. `normalize_choices` records how many options were recommended
(`data.recommended_count`); when it was more than one, the autonomous ladder escalates
instead of taking the kept recommendation. A parked multiple-choice question carries the
`Option N` labels in its exposed `discussion`.

Sizing verdict: `SUBTASK_MAX` is 6. `assess` keeps unsure sizing at `compound` (it no longer
defaults up to `plan_shaped`) and states the verdict for every implementation:
`sizing_reason` (one line, for example "about 9 subtasks across 3 modules, needs a sealed
plan"), `subtask_estimate` and `proposed_breakdown`. In a top-level run, `plan_shaped`
raises the hard-trigger `sizing_verdict` escalation (the autonomous ladder never answers it)
stating the verdict and its reason, with three options: "Hand it to the architect"
(recommended), "Do it here anyway (up to 6 subtasks)" and "Narrow the scope". Only an exact
option (its label, its number or its whole text) or the `narrow` instruction answers it; any
other text, a negated "don't hand it to the architect" included, picks none and ends at
`end_redirect` with nothing written. The architect option writes
`<git root or project_dir>/plans/engineer-handoffs/<slug>.md` (the run id is added to the
name when the slug is taken; nothing is overwritten, and when both names are taken the run
says so and redirects; a `plans/` or `engineer-handoffs/` that resolves outside the project,
such as a committed symlink, is refused the same way) with `status: ready`,
`vehicle: architect`, `project:`, `created:` and `title:` frontmatter and a body carrying the
brief, the clarifications, the intent, the sizing verdict, the proposed breakdown and the
acceptance criteria; it ends at `end_handoff` (`SISYPHUS_HANDOFF`) naming the path and saying
that a bare "go ahead" in architect-next picks it up. A smoke row runs architect-next's own
`_find_seed` and `_seed_question` on the written file. When the file cannot be written, the
text goes to `architect-handoff.md` in the run dir and the run ends at `end_redirect` naming
it (a failing run-dir copy is ledgered and named too). A delegated run that somehow reaches
the architect option writes nothing and ends at `end_redirect`, and architect-next reads
`SISYPHUS_HANDOFF` as a no-work sentinel as a backstop. "Do it here" goes to `plan_subtasks`
with a `sizing_note` telling the planner to fit the work into at most 6 subtasks. "Narrow the
scope" asks for the narrower scope as free text (the
hard-trigger `sizing_narrow` question at `ask_user`), makes it the brief with the original
request below it as context and runs `assess` again; an Other reply that already names the
narrower scope is the `narrow` instruction and goes straight there. A picked-up `vehicle:
sisyphus` handoff is consumed when the run writes the architect handoff or does the work here,
and stays ready while the scope is narrowed or when no architect handoff was written. A
delegated run keeps today's behaviour: it never asks and ends at `end_redirect`
(`SISYPHUS_REDIRECT`), the parent owning the planning.
`record_subtasks` still enforces the cap: a top-level plan over 6 subtasks (or none) is never
trimmed or dropped but raises `sizing_verdict` again with the planner's breakdown and only the
architect and narrow options, while a delegated one ends at `end_redirect`. `sizing_rounds`
bounds the verdicts at `CLARIFY_MAX` (3) per run; past it `sizing_cap` asks with the verdicts
as evidence: do it here on a stated reason (recommended until one such extension was granted,
then the architect handoff is), hand it to the architect, or stop. `clarify_rounds` caps
clarification the same way through `clarify_cap`. Neither round counter is ever reset; the
extensions are counted in `sizing_extensions` and `clarify_extensions`. The
wrapper's ignored `choice_and_sizing_smoke_rows_go_red_under_the_recorded_sabotages` tail
turns the key rows red.

## Per-subtask review and the final whole-task review

A compound run works through its sealed subtasks one at a time. Each subtask's review round
checks that subtask's own outcome, constraints, acceptance criteria and any amendment the user
made to them (`build_gauntlet_prompt` writes them as the `Plan / acceptance criteria:` block,
with a scope line saying later subtasks deliver the rest), and the coder sees the parent task's
criteria as context only.

`next_subtask` records the worktree's tree when a subtask starts (`subtask_tree`, uncommitted
earlier work included; re-entry carries it), and the change check compares content against it,
the planning store left out. A subtask that changed nothing (a read-only or research step)
skips its conformance review, so it is never failed for having no implementation. A HEAD that
moved only by commits that are on the upstream branch and were made before the subtask started,
the worktree matching it, is a pull: no change. The run base moves past such a pull only while
no earlier subtask has committed (HEAD still at the run base; uncommitted earlier work stays in
the diff either way); after that the pulled commits stay in the whole-task diff.
When nothing commits between subtasks the review's `Diff:` also carries earlier subtasks' work,
so the prompt names the files this subtask changed.

A strikeout while the worktree holds earlier subtasks' uncommitted work saves the failed
attempt as a commit under its own `refs/sisyphus-next/strikeout/` ref (never overwritten) and
puts back only the paths it changed, index included; if that save fails, or elsewhere, it
stashes as before. A passed or accepted subtask round goes to
`next_subtask`, never to the publish tail. After the last subtask `next_subtask` starts one
final whole-task review (`final_review`, the diff from `run_base_sha`, the parent task's
`spec_text` with the subtask amendments listed as settled rulings, fresh round budgets, and a
whole-task coder brief carrying every scope guard the subtasks collected) through
`review_gate`; only that review goes on to the observability pass and publishing, so every
parent acceptance criterion is still enforced. A single-subtask run is reviewed against the
task's criteria once, as before.
